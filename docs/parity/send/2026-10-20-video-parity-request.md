# 需求单：寄快递页 7 项生产端一致性修复（2026-10-20 视频反馈）

## 一、来源与判定原则

- 来源：用户录制的 RN App 操作视频 `Record_2026-10-20-13-43-27 (1).mp4`（40.04s）中观察到的 7 个现象。
- 判定原则（用户明确要求）：
  1. 现象只是线索，**结论必须由代理自行复核**（真机复现 + 像素量测）；
  2. 必须结合**生产端安装包**取证，必要时读生产端实现逻辑（AOT 快照字符串 / 类名 / 接口路径），不能只按截图猜样式；
  3. 无法取证的部分**不得编造**，要标注为未决项并说明缺什么证据。

## 二、范围

- 目标页面：RN `寄快递`（`src/pages/express`）及其弹层、以及与这些弹层共用的基件。
- 生产端基线：`com.deppon.dpapp` 4.0.7.0。
- 交付物：代码改动 + 逐项对照证据 + 静态门禁通过 + 交接文档。

## 四、非目标（本轮不做）

- 生产端增值服务里的 `双人派送`、`通电验机`、`拍照服务（拍照签收 / 取货照片）`：RN 下单载荷无对应字段，**不为了视觉一致而伪造**，等接口契约。
- 协议弹层的版本历史接口对齐（本轮以既有 H5 `PROTOCOL_RECORD` 承接）。
- 生产端未选中态时效卡（该账号只有 1 个产品，取不到样本）。

## 五、证据要求

1. 每条需求至少一份生产端真机截图（含控件 bounds / 颜色量测数据）。
2. 涉及「生产端是否存在该页面/字段」的判断，需附包内证据（AOT 字符串、类名、接口路径）。
3. 每条改动附 RN 侧代码位置与门禁结果。
4. 无法取证的部分单列「未决项 + 缺什么证据 + 建议如何补」。

## 六、验收动作

1. 静态门禁全绿：`typecheck`、`lint`、`lint:styles`、`check:styles[:strict]`、`check:rn-boundaries`、`check:routes`、`check:module-size`、`check:business-rules`、`check:runtime-config`、`check:platform-build`。
2. 真机重打包安装后，7 条逐条截图对照（RN vs 生产端）。
3. 交接文档更新（本目录 `2026-10-20-video-parity-report.md`）。
